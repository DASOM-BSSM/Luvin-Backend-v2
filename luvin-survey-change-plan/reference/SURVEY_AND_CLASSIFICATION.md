# 빵 유형 설문·채점·분류 명세 v1 초안

## 1. 목적과 적용 범위

앱은 20개 상황 질문에 대한 답변을 수집하고, Spring은 13개 기본 성향과 7개 보조 지표를 계산한 뒤 8개 빵 유형 중 하나를 선택한다. AI 서비스는 기존 13개 성향으로 행동을 생성한다. 빵 유형은 요약 설명이며 13개 성향을 대체하지 않는다. 보조 지표는 기본적으로 유형 분류에만 사용한다.

이 설문, 가중치, 유형 대표 범위는 제품 문구에 맞춰 만든 **검증 전 초기 가설**이다. 임상적 진단, 애착유형 검사, 실제 관계 지속성이나 궁합 예측을 의미하지 않는다. 구현의 결정성과 측정의 타당성은 별개다.

기존 한 문항당 한 변수 초안을 대체하는 독립 설계안이다. 기존 아키텍처 문서는 자동 수정하지 않았다.

## 2. 앱 안내와 선택 방식

안내 문구: “정답은 없어요. 최근의 나와 가장 가까운 답을 골라주세요. 연애 경험이 없다면 호감이 있는 사람과의 관계에서 예상되는 내 모습을 떠올려주세요.”

문항별 단일 선택이며 20개 모두 응답한다. 앱에는 질문과 답변만 표시하고 변수명·점수·예상 유형은 표시하지 않는다. 현재 세 답변 중 맞는 답이 없다는 사용성 피드백이 많으면 문구 또는 문항을 수정한다. 중간 답변을 무조건 '모르겠음'으로 취급하지 않는다. 경험에 기반한 답변과 예상 답변이 섞인다는 한계도 후속 검증에 포함한다.

아래 매핑 표기에서 `+1`은 높은 방향, `−1`은 낮은 방향, `0`은 중간 방향의 근거다. 최종 점수에 그대로 1점을 더한다는 뜻이 아니다. 각 문항의 주 측정 변수는 모든 답변에서 **가중치 2**, 추가 변수는 **가중치 1**로 반영한다. 표에 없는 변수는 관찰하지 않은 것으로 처리한다. 명시된 0은 중간을 지지하므로 분모에 포함하며, 미측정은 분자·분모 모두에 포함하지 않는다.

부차 매핑은 답변 문구에 근거가 있는 경우만 붙였다. 사교적 접근성을 연애 주도성으로, 행동적 돌봄을 현실 우선성으로, 느린 속도를 관계 회피로 자동 변환하지 않는다.

## 3. 질문 20개와 답변별 매핑

### 1. 좋아하는 사람과 더 가까워지고 싶을 때, 나는?

문항 ID: `q01` · 주 측정: **관계 주도성** (가중치 2)

1. 이번 주에 같이 할 일을 정해서 먼저 만나자고 한다.  
   → 관계 주도성 +1 × 2 / 관계 속도감 +1 × 1

2. 가볍게 만나자고 말하고, 구체적인 일정은 함께 정한다.  
   → 관계 주도성 0 × 2

3. 상대가 먼저 만나자고 할 때까지 기다리는 편이다.  
   → 관계 주도성 -1 × 2

   → 관계 불안도 +1 × 2 / 확신 요구도 +1 × 1

2. 편한 이야기부터 나누며, 아직 어려운 이야기는 남겨둔다.

3. 내 깊은 마음까지 보여주는 건 부담스러워 혼자 간직한다.  
   → 관계 회피성 +1 × 2 / 감정 억제성 +1 × 1

3. 상대의 일이 내 일처럼 느껴져, 내 기분도 한동안 가라앉는다.  
   → 감정 동조성 +1 × 2

### 5. 많이 끌리는 사람과 생활 방식이나 미래 계획이 꽤 다르다면?

## 4. 점수 계산

각 지표 j에 대해 선택된 답변의 방향 r(-1,0,+1)과 근거 가중치 w를 모은다.

```text
S_j = Σ(w × r)
W_j = Σw
보정된 방향 z_j = S_j / (2 + W_j)
점수 x_j = 50.5 + 49.5 × z_j
```

2는 중간값을 지지하는 가상 근거량(prior weight)이다. 근거가 한 문항뿐인 경우 극단 점수로 단정하는 것을 줄인다. 1~100의 정확한 중간값은 50.5다. 내부 연산은 반올림 전 값을 사용하고 API 표시용 점수만 소수 둘째 자리 half-up 반올림한다. 모든 변수에 같은 공식을 적용한다.

예: 가중치 2의 높은 방향 답변 하나만 있으면 S=2, W=2, 결과는 75.25다. 낮은 방향이면 25.75, 중간이면 50.50이다. 추가로 가중치 1의 낮은 방향 근거가 있으면 S=1, W=3, 결과는 60.40이다. 이 예는 반대 방향 답변을 오류로 처리하지 않고 종합한다는 뜻이다.

모든 primary 문항은 세 답변 모두 같은 지표를 측정하므로 어떤 경로로 답해도 20개 지표에 가중치 2 이상이 확보된다. 단, 보조 매핑은 선택에 따라 관찰량이 달라진다. 이는 중립 근거와 다르며 분류 결과와 함께 W를 기록한다. 지표마다 한 개의 직접 문항밖에 없고 반복 측정 정도도 고르지 않으므로 정밀 척도라고 주장하지 않는다.

### 근거 상태

각 지표에 `evidence_weight`, `observations`, `direction_conflict`를 저장한다. direction_conflict는 +방향과 −방향 근거가 모두 존재한다는 뜻이다. 이는 거짓 답변을 의미하지 않고 상황에 따라 다른 행동일 수 있다. 근거량이나 충돌 여부를 '통계적 신뢰도'로 표시하지 않는다.

누락 답변은 중간점수로 자동 대체하지 않고 제출 오류로 처리한다. 동일 문항 중복, 존재하지 않는 답변 ID, 다른 설문 버전의 ID도 거부한다. 수정 응답은 전체 답변에서 다시 계산하고 이전 점수에 델타를 누적하지 않는다.

특정 유형과 잘 맞거나 만나면 힘들다는 궁합 문구는 이 계산에서 나오지 않는다. 궁합을 제공하려면 별도의 정의와 평가가 필요하다.

## 6. 분류 알고리즘

각 유형 t의 지표 j 대표 범위를 [L,U]라 할 때:

```text
d_j = max(L - x_j, 0, x_j - U)
D_t = sqrt(Σ(유형 중요도 × d_j²) / Σ유형 중요도)
```

범위 안이면 차이는 0이다. D가 가장 작은 유형을 선택한다. D는 원점수 기준 거리이며 확률이나 검증된 적합률이 아니다. 서로 다른 변수 집합을 사용하는 유형들의 거리 비교는 휴리스틱이므로 유형별 선택 편향을 반드시 확인한다. 관찰량을 유형 가중치에 다시 곱하지 않는다. 점수 보정에 이미 반영했기 때문이다.

### 경계 처리

- 1등과 2등 거리 차이가 3 미만이면 `mixed=true`.
- 1등 거리도 18 초과이면 `poor_fit=true`.
- 두 값은 초기 운영 가설이며 사용자 정답 데이터로 검증된 경계가 아니다.
- 거리가 0인 유형이 여러 개면 자연스럽게 mixed가 된다. 무작위로 결과를 바꾸지 않는다.
- 거리 차이가 소수 6자리에서 같으면 설정에 고정된 tie-break 순서로 하나를 선택한다. 순서 자체에 심리적 의미는 없으며 동점은 기록한다.
- 제품상 반드시 하나를 보여줘야 하면 primary_type을 반환하되 mixed/poor_fit인 경우 결과 문구를 '이 설문에서는 ○○에 가장 가깝게 나왔어요'로 제한한다. secondary_type은 내부 분석용으로 저장하고 필요 시 UI에 노출한다.
- 모든 답변이 중간 선택인 경우도 유효한 답변이다. 임의로 불성실 응답으로 판단하지 않는다. 다만 거리 동률·작은 간격으로 인해 결과 구분이 어려울 수 있다.

범위 안에서 모든 유형에 0점 거리가 나오는 등의 문제가 평가에서 발견되면 tie-break를 정교하게 만드는 대신 프로필 구분과 문항 설계를 수정한다.

## 7. 설명 생성

유형은 서버의 계산 결과로 고정한다. LLM이 바꾸거나 임의로 '87% 확률'이라고 설명하게 하지 않는다. 초기에는 템플릿으로 충분하다.

각 유형의 feature별로 방향 부합도를 계산한다. 높은 범위는 실제 점수가 50.5보다 높은지, 낮은 범위는 낮은지 확인한다. 중립 반대 방향인 지표를 분류 이유로 사용하지 않는다. `유형 중요도 × |점수−50.5|`가 큰 부합 지표를 최대 3개 고르되, 중간값과 5점 이내는 이유에서 제외한다. 이를 지지하는 실제 선택 문항 ID도 저장한다. 이것은 유형의 특징에 부합하는 근거이며 다른 유형보다 선택된 원인을 완전히 설명하는 인과 분석은 아니다.

예: “말로 마음을 크게 표현하기보다는 직접 챙기는 편이고, 익숙해진 관계에서도 함께할 즐거움을 찾으려는 답변이 두드러졌어요.”

사용자가 선택하지 않은 행동, 영구적인 성격 단정, 애착 진단, 상대와의 궁합은 추가하지 않는다. 뚜렷한 근거가 없으면 '여러 성향이 비슷하게 나타났으며, 현재 분류 기준에서는 ○○에 가장 가깝습니다'처럼 제한한다.

## 8. 앱·Spring·AI 서비스 연동

```text
앱: survey_version + 문항별 answer_id 제출
  ↓
Spring: 버전과 20개 응답 검증
  → 지표별 score/evidence 계산
  → 8개 profile 거리 계산
  → primary/secondary/flags/evidence 저장
  ├→ 앱: 유형, 제한된 설명, 필요 시 혼합 성향 안내
  └→ AI 서비스: 13개 core 점수 + 성격 + 분류 결과/version
```

앱이 점수나 유형을 보내더라도 서버 결과를 최종값으로 사용한다. 화면 순서를 바꾸더라도 답변 ID로 매핑하고 배열 인덱스로 채점하지 않는다. 문항/답변 표시 순서를 무작위화한다면 실제 표시 순서도 별도 기록하여 순서 편향을 평가한다.

저장 필드: survey_version, scoring_version, classification_version, answer IDs, core scores, auxiliary scores, evidence weights/counts/conflicts, 유형별 거리, primary/secondary, mixed/poor_fit/tie, explanation evidence, calculated_at. 점수/응답은 민감한 성향 정보로 접근 제한하고 일반 로그에 남기지 않는다.

설문 문구나 답변은 survey_version, 가중치·점수식은 scoring_version, 유형 프로필·경계·동점 규칙은 classification_version을 올린다. 과거 응답에 새 결과를 계산할 때는 새로운 결과 레코드를 만들고 과거 결과를 덮어쓰지 않는다. 진행 중 시즌은 시작할 때 복사한 성향과 분류 버전을 유지한다.

## 9. 구현 검증과 제품 검증

### 구현에서 보장할 것

- 모든 질문 3개 답변, ID 유일, 13 core+7 auxiliary, 모든 선택 경로에서 primary 지표 관찰.
- 같은 답변·설정 버전은 같은 점수·유형·동점 결과.
- 미측정과 중간 근거의 분모 차이, 상충 근거의 보정, 범위와 반올림 정책.
- 누락/중복/잘못된 버전 또는 답변 거부. 서버 계산과 앱 표시 버전 일치.
- 일부 답변 변경 시 이전 점수 누적 없이 재계산.

### 출시 전 제품에서 확인할 것

- 각 유형의 전형적 프로필과 경계 프로필을 사람이 먼저 정의하고 결과 비교.
- 특히 크림빵–프레첼, 소금빵–바게트, 도넛–카스테라 혼동 확인.
- 전체 중간, 전체 첫 번째, 전체 마지막 선택과 혼합 응답에서 특정 유형 쏠림 확인.
- 한 문항만 바꿀 때 결과가 과도하게 바뀌는 구간 확인. 모든 변경에서 유형 불변을 요구하는 것은 아님.
- 실제 설문 테스트에서 답변을 읽고 이해하는 방식, 억지로 골라야 하는 문항, 결과 설명의 납득도를 수집.
- 독립적인 사람이 익명 프로필을 보고 붙인 유형과 비교하고, 평가자끼리도 자주 불일치한다면 유형 정의부터 수정.
- 가중치 튜닝에 쓴 자료와 최종 평가 자료를 분리. 인위적인 균등 무작위 응답 분포를 실제 사용자 분포로 해석하지 않음.

이 단계가 끝나기 전 '분류 정확도'나 '심리검사 신뢰도'를 수치로 홍보하지 않는다. 문항 수 20개라는 제약상 일부 지표는 반복 측정이 부족하고 보조 특성도 완전하지 않다.

## 10. 함께 제공한 파일

- `survey_config.json`: 실제 20문항·답변 ID·매핑·유형 프로필·버전.
- `classifier.py`: 외부 의존성 없는 Python 참조 구현. Spring에서 같은 규칙으로 이식할 수 있음.
- `example_result.json`: 중간 답변 경로의 기계 생성 예시. 실제 사용자 결과가 아님.
- `validation_report.json`: 구성·결정성·샘플 경로 확인 결과. 심리측정 타당성 검증 결과가 아님.

정확한 점수 정렬에는 내부 유리수 연산을 사용하고 표시용 값만 반올림한다. 프로덕션의 인증·DB 저장·설명 문구 API는 이 참조 구현 범위 밖이다.

## 11. 이번 초안의 기계적 확인 결과

고정 seed로 답변을 균등 무작위 선택한 가상 응답 10,000개를 확인했다. 모든 점수는 범위 안에 있었고, 8개 유형 모두 실제로 선택되는 경로가 존재했다. 같은 입력의 결정성, 중간 응답 점수, 잘못된 입력 거부도 확인했다.

유형 선택 수: 크림빵 1,376 / 팥빵 705 / 소금빵 440 / 프레첼 1,590 / 도넛 1,787 / 바게트 912 / 마들렌 2,360 / 카스테라 830. 혼합 성향 flag는 4,390개, 낮은 적합도 flag는 303개였다.

균등 무작위 선택은 실제 사람의 응답 분포가 아니다. 그럼에도 현재 설계에서 마들렌이 상대적으로 자주, 소금빵이 드물게 선택되고 혼합 flag가 많이 발생한다는 점은 검토 대상이다. 이는 출시 준비 완료가 아니라 작동 가능한 초기 분류기라는 의미다. 실제 대표 사례와 사용자 응답을 확인한 뒤 문구/범위/가중치/혼합 경계를 조정해야 한다. 유형을 무조건 같은 비율로 만들기 위해 조정하지 않는다.

## 12. 실행 예시

Python 3.12에서 별도 패키지 설치 없이 실행할 수 있다. 이 폴더를 작업 디렉터리로 삼는다.

```bash
python3 classifier.py survey_config.json
python3 classifier.py survey_config.json answers.json
```

첫 명령은 전부 중간 답변을 선택한 가상 결과다. 실제 제출 예시는 `sample_answers.json`에 있다. `answers.json`은 동일 구조에 실제 선택 ID를 넣으면 된다. 이 구조의 JSON을 Spring에서 검증하고 동일 규칙을 이식할 수 있다.

참조 구현의 config 검사는 개발용 assertion을 사용한다. 운영 서비스에는 별도의 schema validation, 크기 제한, 인증, 소유권 검사와 적절한 HTTP 오류 변환을 구현해야 한다.
